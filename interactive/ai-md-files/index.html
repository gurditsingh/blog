What problem are AI markdown files solving?

Enterprises are not struggling because models are weak. They are struggling because context is fragmented, repeated, and lost between sessions, tools, teams, and repositories.

Repeated prompting

The same repository conventions, commands, and architecture notes get pasted again and again.

Unclear boundaries

Agents mix architecture facts, team rules, and task-specific playbooks into one giant prompt.

Poor portability

Teams use Codex, Claude, Copilot, Cursor, Windsurf, and Gemini CLI, but each tool needs the same project truth.

How the hierarchy works

The cleanest setup uses layered context instead of one giant instruction file.

Canonical layers

Specs
Stable project truth: purpose, architecture, phases, commands, constraints.
Rules
Persistent behavior: validations, boundaries, response expectations, forbidden actions.
Skills
Reusable procedures: analyze ETL artifacts, create templates, design lakehouse layers, generate PySpark.

Practical mapping

Codex → AGENTS.md + .codex + skills Claude → CLAUDE.md + rules + skills Copilot → repo instructions + path rules + prompt files Cursor → rules + AGENTS.md Windsurf → rules + workflows Gemini CLI → GEMINI.md + skills

High-level ETLModernization example

This project structure demonstrates how a real enterprise repo can separate project truth, behavior, and reusable workflows.

Area Purpose Example files
Canonical entry point Tell every agent what the repo is, how it works, and where to look next. AGENTS.md
Specs Store the stable project truth for both phases and the Lakehouse design. ai/specs/project-spec.md, phase-1..., phase-2...
Rules Keep persistent behavior concise and testable. ai/rules/core-rules.md, lakehouse-rules.md
Skills Package repeatable procedures like discovery, template generation, and Databricks PySpark generation. .agents/skills/*/SKILL.md
Adapters Map the same project into Codex, Claude, Copilot, Cursor, Windsurf, and Gemini CLI. CLAUDE.md, .github/, .cursor/, .windsurf/

Prompt-only vs disciplined repo-native setup

A quick comparison of how teams evolve from experiments to enterprise usage.

Prompt-only stage

  • Context lives in chat history
  • Conventions must be re-explained
  • Different tools drift apart
  • Hard to audit and review
  • Low repeatability across teams

Repo-native discipline

  • Project truth lives in version-controlled files
  • Behavior becomes consistent
  • Portable skills reduce duplication
  • Tool adapters stay thin
  • Enterprise governance becomes practical
